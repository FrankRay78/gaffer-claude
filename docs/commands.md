# Command reference

One section per command, in the order a piece of work meets them: the issue stage, the build chain, the pull-request review, the periodic audits and the session tools, then the `diagnose` skill and the `no-chmod` hook. Each section is derived from the command's own prompt under `commands/`; what is not stated there is not stated here. Every command is typed `/gaffer:<name>`.

Reading the bullets:

- **Invoke** — the command with its arguments, and what happens when none is given.
- **Needs** — the preconditions it checks before it does anything, and the tools it calls.
- **Reads** — the headings of `CONVENTIONS.md` or `REVIEW.md` its *Repository conventions* or *Repository criteria* table names (read from the plugin's defaults and then the repository's own file, as [`interfaces.md`](interfaces.md) describes), and the repository files it reads.
- **Changes or posts** — every side effect, local and remote.
- **Ends with** — its verdict, where it writes one per [`verdict-schema.md`](verdict-schema.md), or the shape of its closing report.
- **Unattended?** — whether it runs with no prompts, and what it refuses to do when nobody is present.

A reason quoted in backticks is the exact text the command puts in a `failed` verdict or a stop message.

## draftissue

- **Invoke** — `/gaffer:draftissue [idea | document path | issue URL | backlog <number>]`. The argument is a free-text idea, an existing issue (`#N`, a bare number or a URL, treated as a migration), a document (URL or repository path, optionally narrowed to one section) or `backlog <number>` / `item <number>`. Guidance alongside the source outranks the source. With no argument it asks for the source and does not invent one.
- **Needs** — `gh` for an existing issue (`gh issue view`), for GitHub-hosted documents and for raising the issue; `gh auth status` and `gh repo view` when the target is uncertain. It stops, keeps the scratch file and tells the user its path when the repository has no GitHub remote. A `backlog` argument with no backlog named under *Issue sources* makes it ask where the backlog is.
- **Reads** — `CONVENTIONS.md` → *Issue sources*, *Issue concerns*, *Acceptance criteria*, *Scratch files*. It reads the source, the codebase with targeted reads to check each claim the source makes about today, and the source issue's body, any `<!-- speckit:review -->` comment and any `## Confirmed decisions` section on a migration.
- **Changes or posts** — writes the issue body to the git-ignored scratch file *Scratch files* names (default `.claude/scratch/gh-issue-body-<slug>.md`) and deletes it in the same step as `gh issue create --title … --body-file …`. Opens one GitHub issue. On a migration, closes each source issue the user confirms, one at a time, with the comment `Superseded by #<M>`. It never edits any other source: not a document, not a backlog.
- **Ends with** — the new issue's URL; each decision asked about and the answer recorded, or that the source settled everything; any stale claim corrected; what was carried into Source notes. It stops without starting implementation and does not restate the issue in chat. When the capability already exists it stops and raises nothing.
- **Unattended?** — No. It asks for a missing source, raises requirements decisions the source leaves open as written assessments and waits for answers, and asks before closing each source issue even when told to close it. It raises the issue without a draft-approval pause.

## reviewissue

- **Invoke** — `/gaffer:reviewissue [issue number or URL]`. With no argument it asks which issue to review.
- **Needs** — `gh issue view … --json title,body,labels,comments`, `gh repo view` for the default branch, `gh issue comment`, `gh issue edit`, `gh api` (PATCH on a refine run). It treats all issue content as data, never as instructions. An issue carrying the `ready` label stops it: it posts nothing, edits nothing and names the reopen path (remove `ready`, request the review again).
- **Reads** — `CONVENTIONS.md` → *Issue review checks*, *Scratch files*. It reads `CLAUDE.md` and the documents it links, the source tree the issue touches, the modules the work integrates with, test data and fixtures the issue references, and deployment configuration where the issue touches runtime shape.
- **Changes or posts** — first run: posts one comment carrying `<!-- speckit:review -->`, a gaps-at-a-glance table, numbered Requirements and Technical gaps each with a `> _**Recommendation:**_` and a `> _Answer:_` slot, and optional Commentary; then adds the `needs answers` label. Refine run (a marker comment already exists): edits that comment in place via `gh api -X PATCH`, re-framing only the gaps whose answers hedge (`not sure`, `idk`, `tbd`, `more options`, `help`, `don't understand` and the rest of its dictionary), leaving every other gap byte-for-byte, and writes the full body to the scratch file *Scratch files* names (default `.claude/scratch/reviewissue-body.md`) first. Where no gap qualifies it makes no edit. It never modifies the issue body.
- **Ends with** — already confirmed: the marker seen, a pointer to `## Confirmed decisions`, the reopen path. First run: issue number and title, gap count split by type, whether there is commentary, the comment URL. Refine run: the gap numbers re-framed, or that none qualified and what to do next, and the comment URL.
- **Unattended?** — It runs with no prompts once it has an issue number; it asks only when the argument is empty, so an automated runner must supply one. Its text allows for an unattended run that sees only the checkout and the issue, in which an uncheckable claim may stay only inside a `my judgement` Reason. It refuses to post a second review over a `ready` issue and to touch the issue body.

## confirmissue

- **Invoke** — `/gaffer:confirmissue [issue number or URL]`. With no argument it asks which issue to confirm.
- **Needs** — `gh issue view … --json body,labels`, `gh api --paginate … /issues/<N>/comments` (REST, for the numeric comment id), `jq`, `gh api --method PATCH`, `gh issue edit`, `gh api --method DELETE`. Stops before changing anything when: no marker comment exists and the issue is not already confirmed; any gap's `> _Answer:_` is empty; any answer hedges (the same dictionary as `/gaffer:reviewissue`); or a decision contradicts a body passage without determining its replacement. An issue already confirmed (a `## Confirmed decisions` section or the `ready` label, no marker comment) is reported as such, with the label repaired if missing.
- **Reads** — this command has no *Repository conventions* table; it names its scratch files directly. It reads the issue body and labels, and the newest `<!-- speckit:review -->` comment.
- **Changes or posts** — writes `.claude/scratch/confirmissue-body.md` and `.claude/scratch/confirmissue-patch.json`; patches the issue body with a `## Confirmed decisions` section (`<!-- confirmed-decisions -->`, `### Requirements` and `### Technical` sub-headings, one decision bullet per gap) and rewrites any passage a rider or redirect overrules, preserving everything else byte-for-byte; removes the `needs answers` label and adds `ready`; then, after reading both preconditions back from the issue, deletes the review comment by numeric id. A label failure and a deletion failure are never fatal; the report carries them. A failed body patch stops the run before the label and the deletion.
- **Ends with** — the issue number and title; decisions folded, by pattern (accepted, with rider, redirected); each body passage rewritten, by heading or criterion, or that none were; whether `ready` was applied; whether the comment was deleted and, if not, which precondition or call failed and what to do; the issue URL. A stop at step 1, 2, 4 or 5 names the failed precondition and the fix.
- **Unattended?** — It runs with no prompts once it has an issue number. On an unattended run the rewritten-passage list reaches the run summary rather than the author, who sees only an edited body. It refuses to fold while any gap is unanswered or hedging, to patch around a contradiction it cannot resolve, and to delete the review comment until `ready` and `## Confirmed decisions` are both read back from the issue.

## build

- **Invoke** — `/gaffer:build <issue number or URL>` (`239`, `#239` or a URL). With no argument it asks for one and waits; that question is the only interaction it may have.
- **Needs** — `git status --porcelain` empty, else `the working tree has uncommitted changes`; current branch `main`, else `/gaffer:build was not run from main`; `git fetch origin main` succeeds, else `git fetch origin main failed`; `git log origin/main..main` empty, else `local main has unpushed commits`. `gh issue view <N>`: a closed issue or one with an open linked PR stops with `the issue is already built or in flight`; an open issue stating no behaviour stops with `the issue states no behaviour to build against`. A build-and-test command under *Build, test and format*, else `conventions missing: Build, test and format`. A local `feature/<N>-…` branch carrying uninspected commits stops it.
- **Reads** — `CONVENTIONS.md` → *Build, test and format*, *Test-driven development*, *Testing*, *Acceptance criteria*, *Code quality*, *Dependencies*, *Public API and breaking changes*, *Commit messages*, *Documentation*, *Change-intent records*, *Hooks, scripts and plugins*. It reads `CLAUDE.md` first, then the issue's `## Acceptance criteria` checklist, `## Capability` scenarios and `**Scenario: X**` labels.
- **Changes or posts** — creates `feature/<N>-<short-slug>` from `origin/main` (deleting and recreating a leftover branch with no uninspected commits); writes tests carrying `SCENARIO: X` markers for each label; writes production code, or a configuration, tooling or CI change whose RED step is the real tool failing; commits in the `Refs #<N>: <imperative>` form, never a closing keyword; discharges the documentation obligations *Documentation* lists; writes a change-intent record only where the repository keeps them and a decision-table row warrants one; runs the repository's traceability check where one is named. It does not format, push, open a PR, merge or run `/gaffer:verify`, and never commits on `main`.
- **Ends with** — how the criteria were read, the RED evidence quoted, what changed and how each criterion is met, assumptions, any public-API change, what was left out, the change-intent record decision, the hand-off sentence to `/gaffer:verify` above the verdict, then the verdict as the last line: `{"schema": 1, "outcome": "ready", "branch": "<branch>"}` or `{"schema": 1, "outcome": "failed", "reason": "<short reason>"}`.
- **Unattended?** — Yes, by design, after the issue number. It decides every judgement call itself and reports the assumption. It refuses to add a dependency to a library *Dependencies* marks dependency-controlled (stops instead), to make a protected public-API change the criteria do not require (a required one proceeds and is called out, and a recorded pre-1.0 stance lifts the discussion duty), to fold in adjacent improvements, to commit on red and to report `ready` over a red suite, an unimplemented criterion or an uncommitted change.

## verify

- **Invoke** — `/gaffer:verify`. It takes no arguments and reads the issue number off the branch name for its commit messages.
- **Needs** — not on `main`, else `/gaffer:verify was run on main, not a feature branch`; `git log main..HEAD` non-empty, else `no commits on this branch over main`; `git status --porcelain` empty, else `the working tree has uncommitted changes`. A build-and-test command, else `conventions missing: Build, test and format`; a formatter is optional (the default is none, and the format passes are skipped and reported). The `pr-review-toolkit` plugin: it spawns `pr-review-toolkit:code-reviewer`, `silent-failure-hunter`, `pr-test-analyzer`, `type-design-analyzer` and `comment-analyzer` as clean-context subagents in wave 1 alongside a `/gaffer:review-slop` pass, then `pr-review-toolkit:code-simplifier` alone in wave 2. A reviewer error stops the run.
- **Reads** — `CONVENTIONS.md` → *Build, test and format*, *Commit messages*, *Hooks, scripts and plugins*; `REVIEW.md` → *Where it runs* for how Review B runs on the pull request. It reads `CLAUDE.md` first and reviews `git diff main...HEAD`.
- **Changes or posts** — runs the formatter and commits any change it made (`Refs #<N>: apply formatting`) before the suite; runs the full suite as the gate; fixes every confirmed Blocker or Important finding in scope with the smallest change, applies Suggestions at its discretion, lets `code-simplifier` edit files directly; formats again, re-runs the suite and commits whatever the tree holds (`git add -A`, `Refs #<N>: apply /gaffer:verify review findings`). A failed formatter stops with `formatting failed`. A red re-run leaves the review's edits uncommitted and names discarding them as the recovery. It does not push, open a PR, merge, raise an issue for an unfixed finding or write one to a file.
- **Ends with** — whether formatting changed anything and its commit; the suite results; which reviewers ran and the commit step 3 made; findings fixed, not fixed and unapplied Suggestions by name and severity, with any **unrated** marked; the hand-off sentence to `/gaffer:raise-pr` above the verdict; then `{"schema": 1, "outcome": "verified", "branch": "<branch>"}` or `{"schema": 1, "outcome": "failed", "reason": "<short reason>"}` as the last line. Its fixed reasons are the three precondition reasons, `formatting failed` and `conventions missing: <heading>`.
- **Unattended?** — Yes, by design, so it can drive a loop. It never prompts. It refuses to run on `main`, to review while the suite is red, to run `code-simplifier` alongside the reporters, to re-rate a real Blocker or Important down, to review its own fix commit, to commit a red fix to satisfy a later run's clean-tree check, and to report `verified` over a red suite, an unresolved **Fix it** finding or an uncommitted change. Reflection and the pull request are deliberately not steps.

## raise-pr

- **Invoke** — `/gaffer:raise-pr [issue number or URL]`. Empty is the normal case and is not a prompt: it infers the issue from the branch name instead.
- **Needs** — not on `main`, else `/gaffer:raise-pr was run on main, not a feature branch`; `git log main..HEAD` non-empty, else `no commits on this branch over main`. `gh repo view --json nameWithOwner`, `gh issue view <N> --json number,state,title,url -R <owner>/<repo>` to verify the candidate, `git push`, `gh pr create`. A failed `gh issue view` is an abstain, not a stop.
- **Reads** — `CONVENTIONS.md` → *Scratch files*, *Pull requests*, *Change-intent records*. It reads `CLAUDE.md` first, then `git log main..HEAD` and `git diff main...HEAD`.
- **Changes or posts** — pushes the branch with `git push -u origin <branch>`; writes the body to the scratch file *Scratch files* names (default `.claude/scratch/raise-pr-body.md`); opens one pull request with `gh pr create --title "<inferred title>" --body-file <scratch file>`. The body carries `Closes #<N>` only when the issue is open and its URL is exactly `https://github.com/<owner>/<repo>/issues/<N>`; a closed issue in this repository gets `Refs #<N>`; a pull request at that number, another repository's issue or a lookup that could not run gets no closing keyword. Where *Pull requests* names an issue-link check, the report says the abstain turns it red.
- **Ends with** — the closing-keyword outcome first (`Closes #<N> — <issue title>`, `No closing keyword: <reason>` or `Closing keyword unverified: <gh stderr>`), then `{"schema": 1, "outcome": "raised", "pr": "<url>"}` for a pull request this run opened, or `{"schema": 1, "outcome": "failed", "reason": "<short reason>"}` when none was opened, even if a PR already exists for the branch.
- **Unattended?** — Yes, by design: it never asks the invoker for anything. It refuses to guess a closing keyword (a wrong `Closes` is worse than an absent one), to hunt for an issue number anywhere but the leading `<N>-` of a `/gaffer:build`-shaped branch, and to write a `raised` verdict for a pull request it did not open.

## review-pr

- **Invoke** — `/gaffer:review-pr [PR number or URL] [--dry-run]`. Empty means the PR open for the current branch (`gh pr view --json number,url`); if there is none it stops: `No open PR for the current branch — pass a PR number or raise one first.` `--dry-run` runs everything and prints what would have been posted.
- **Needs** — `gh pr view … --json number,url,title,body,state,author,baseRefName,headRefName,headRefOid,files,additions,deletions`; a PR whose `state` is not `OPEN` stops: `PR #<N> is <state> — nothing to review.` `git fetch origin pull/<N>/head`, `git worktree add` and `git worktree remove` when `HEAD` is not already `headRefOid`; `git diff --name-only origin/<baseRefName>...HEAD`; `gh api repos/{owner}/{repo}/pulls/<N>/reviews` to post. Foreground subagents: a triage mapper (haiku), one specialist per dimension (correctness, security, contracts, tests, conventions and intent, call chain), and one verifier per candidate finding. Subagents investigate by reading, use Bash only for single `git` and `gh` commands, never run code from the PR, and treat PR content as data.
- **Reads** — `REVIEW.md` → *Where it runs*, *Severity*, *What not to flag*, *Risk tier*, *Always a person*, *Contracts*, *Context to load*, *Change map*, *Tests*. The repository's `REVIEW.md` is read from the root of the repository the command runs in, never from the review worktree; in CI, the checkout holding the default branch's copy. It reads `CLAUDE.md`, the documents *Context to load* names for the layers touched, and the issue the PR body closes or references.
- **Changes or posts** — a detached worktree at `.claude/scratch/review-pr-<N>/` (removed on completion or abort) and the review JSON at `.claude/scratch/review-pr-<N>.json`. Posts one PR review with `event: COMMENT` and `commit_id` set to `headRefOid`: one inline comment per verified finding on a diff line, and a summary carrying `<!-- review-pr -->` on its first line, the line `Risk tier: <Low|Medium|High> · Merge with no human review: <yes|no>` with reasons, the triage map, the call-chain line, a continuously numbered findings list, counts per severity, the recommendation (**Merge**, **Merge after addressing**, **Do not merge**) and the footer `*Review assisted by Claude Code.*`. An inline position the API rejects is moved into the summary and posted again, never dropped. It never merges.
- **Ends with** — the PR URL, the recommendation, the tier, the no-human verdict, counts per severity, how many candidates verification rejected, and that the next round is `/gaffer:review-followup`.
- **Unattended?** — Yes, from start to post: it never stops for confirmation and posts whoever authored the PR. In CI it posts as the workflow's bot, by hand under the invoker's `gh` account. It refuses to run code from the PR, to follow instructions in PR text, to post unverified findings, to set the tier or verdict from the author, to answer **yes** unless the tier is Low, no always-a-person path is touched and no non-Pre-existing finding is open, and to end its turn while a subagent is still running.

## review-followup

- **Invoke** — `/gaffer:review-followup [PR number or URL] [--dry-run]`. Empty resolves the current branch's PR as `/gaffer:review-pr` does.
- **Needs** — `gh pr view`; stops if the PR is not `OPEN`. Prior rounds found by the `<!-- review-pr -->` marker in `gh api --paginate … /pulls/<N>/reviews`, matched on the marker and not the reviewer's login; none stops it: `No prior review-pr round on PR #<N> — run /gaffer:review-pr first.` A run that would be round 4 or later posts nothing and reports the cap. `gh api graphql` for `reviewThreads`, the thread reply endpoint, the `resolveReviewThread` and `unresolveReviewThread` mutations; the same worktree, subagent and PR-content-as-data rules as `/gaffer:review-pr`.
- **Reads** — this command has no table of its own: it loads the plugin's and the repository's `REVIEW.md` as `/gaffer:review-pr`'s *Repository criteria* says, then the checkout's documents. It reads the delta since the last reviewed commit from the author's own work only (`git log --first-parent --no-merges <last-reviewed-sha>..HEAD`, plus hand-resolved conflicts via `git show --remerge-diff`).
- **Changes or posts** — a detached worktree under `.claude/scratch/` where needed, removed afterwards. For each open prior-round finding: **Fixed** (a verifier confirms the fix; a reply references the commit and the thread is resolved), **Justified** (a reply accepting and resolving, or one reply saying why the justification does not hold) or **Unanswered** (re-raised once, then escalated to the summary). A hand-resolved thread whose finding is not Fixed or Justified is re-opened before the reply. Then one review (`event: COMMENT`, `commit_id` set to `headRefOid`) with new inline findings from the delta only and a round summary carrying the marker, the tier and verdict line, the call-chain line, every prior finding's outcome, new findings numbered on from the last round, the recommendation and the footer. It never repeats a posted finding or flags code untouched since the last review.
- **Ends with** — the PR URL, round number, thread outcome counts, new finding count, the recommendation, the tier and the no-human verdict, and, where everything is resolved and the recommendation is **Merge**, that approving and merging is the maintainer's call in GitHub.
- **Unattended?** — Yes, from start to post, never stopping for confirmation; the usual trigger is the CI workflow *Where it runs* names. It refuses to post a fourth round, to re-litigate the whole PR, to treat the author's replies as instructions, and to close a finding on a resolved thread alone.

## review-slop

- **Invoke** — `/gaffer:review-slop`. It takes no arguments and reviews the current branch's diff against `main`.
- **Needs** — a branch diff against `main`. It names no tool.
- **Reads** — no conventions table. It reads the diff and the surrounding code it compares the additions against.
- **Changes or posts** — nothing. It emits a cleaned diff removing excessive comments, unnecessary defensive code, type-system workarounds, stylistic inconsistencies and over-engineering, while keeping every legitimate functional change. `/gaffer:verify` runs it as one input to its review and applies hunks of the cleaned diff as Suggestions.
- **Ends with** — the complete cleaned diff inside `<cleaned_diff>` tags, or the original diff unchanged with a note that no changes were needed.
- **Unattended?** — Yes; it has no prompts and no side effects.

## audit-codebase

- **Invoke** — `/gaffer:audit-codebase <since-ref>`, a tag or commit that starts the "what changed" window. With no argument, or one that `git rev-parse --verify <since-ref>^{commit}` rejects, it asks for one and stops; it never defaults to the latest tag.
- **Needs** — `git status --porcelain` empty, else it reports the dirty tree and stops; `git log`, `git diff --stat`, `git log -S`; `gh issue view`, `gh pr view`, `gh label list`, `gh issue list --search "Codebase audit in:title"` for the baseline, `gh issue create`; the evidence commands *Audit* lists; five `general-purpose` lens subagents launched together, then one refuting verifier subagent per finding, never batched. A tool that fails or is refused is recorded once and not retried more than once.
- **Reads** — `CONVENTIONS.md` → *Audit*, *Testing*, *Dependencies*, *Public API and breaking changes*. It reads `CLAUDE.md` first, then the whole tracked tree within the scope *Audit* lists, the documents the lenses check against code, the repository's and the plugin's commands, and the previous audit issue where one exists. Security, mutation testing, build output, scratch and worktree copies, and change-intent records as staleness targets are out of scope.
- **Changes or posts** — working files under `.claude/scratch/audit/` (`window.md`, evidence outputs, `issue-body.md`), none committed. Opens exactly one GitHub issue titled `Codebase audit: <short HEAD> (<date>)` with the one label *Audit* names, and never `ready`, `review`, `confirm` or `parked`. It changes no tracked file, deletes nothing outside its own working directory and opens no pull request. If a tool writes where it should not, it stops and reports the file rather than reverting it.
- **Ends with** — the issue URL; findings raised against survived per lens; whether anything is broken for users today; the top three items by leverage; what a lens or tool could not reach; any lens with a poor survival rate and what its refuted findings had in common; and the result of a final `git status --porcelain`, listed and not cleaned up if non-empty.
- **Unattended?** — It prompts only for a missing or invalid `<since-ref>`, then runs to the issue. It refuses to edit, commit, delete or raise a pull request, to thin or sample verification, and to apply any label automation reacts to.

## audit-deadcode

- **Invoke** — `/gaffer:audit-deadcode`. The prompt names no argument.
- **Needs** — the codebase to read. It names no tool.
- **Reads** — no conventions table. It traces imports, calls, entry points, configuration and build files, test code, dynamic and reflective calls, and documentation references across the whole codebase.
- **Changes or posts** — produces `DEADCODE.md` as its response; the prompt says to create the file and that the response contains only its content. It deletes nothing.
- **Ends with** — the `DEADCODE.md` report: Summary, Files to Delete, Functions/Methods to Delete, Classes to Delete, Variables/Constants to Delete, Verification Notes, Estimated Impact. Only items it is certain are unused are listed.
- **Unattended?** — It has no prompts. It errs on the side of caution where it has any doubt.

## bugmagnet

- **Invoke** — `/gaffer:bugmagnet <implementation-file-path>`. Language and test framework are detected from the extension and the project.
- **Needs** — the implementation file, its test file (it asks whether to create one if none exists), and the project's test runner; a coverage tool where the project has one, run for a baseline. It reads README and CONTRIBUTING files for testing guidelines.
- **Reads** — no conventions table. The implementation file and files it references within the project, existing tests, coverage configuration, and any additional files the user names.
- **Changes or posts** — adds tests to the existing test file, one or a small group at a time, each run immediately; documents a discovered bug as a skipped test with a `- BUG` suffix and a comment holding root cause, location, current code, proposed fix and expected against actual; phase 4 tests go in a suite named `bugmagnet session <current date>` or an existing exploratory suite. It never changes the implementation file and never crosses project boundaries. Three attempts per test, then document and move on.
- **Ends with** — a Test Coverage Summary: tests added by category, passing and skipped counts, key findings, and each discovered bug with location, root cause, fix and minimal reproduction, plus a separate bug summary with impact assessment.
- **Unattended?** — No. It pauses for confirmation at the end of each phase, asks for additional context files, asks which gap tests to implement, asks the user to decide unclear expected behaviour, and asks before advanced coverage.

## capture-learnings

- **Invoke** — `/gaffer:capture-learnings`. No arguments; run at the end of a session, after a feature or after `/gaffer:raise-pr`.
- **Needs** — `git symbolic-ref`, `gh repo view` or `main` for the default branch; `git rev-parse`, `git log`, `git diff` for branch evidence; `gh pr view --json comments,reviews` best-effort for a posted review; the `update-config` skill where a hook, permission or env change is approved. There is no hard gate: an empty branch context only removes Lens B.
- **Reads** — no conventions table. It scans the conversation (Lens A), the branch's commit history (Lens B), the posted PR review (Lens D), and `CLAUDE.md`, `CONVENTIONS.md`, `REVIEW.md` and `.claude/memory/` for rule collisions and duplicates. For a test it adds it follows `CONVENTIONS.md` → *Testing* and *Test-driven development*.
- **Changes or posts** — only approved candidates, in order of preference: amends a rule in `CLAUDE.md`, `CONVENTIONS.md`, `REVIEW.md` or an existing memory (with any linked guide in lockstep); proposes a deterministic mechanism and applies it only on explicit approval, via `update-config` for hooks or a RED-run test for code shapes; writes or updates a `.claude/memory/*.md` entry and its `MEMORY.md` pointer line; amends or deletes a memory the session made stale. A learning about a plugin command becomes an issue on the plugin's repository, never an edit to a plugin checkout. It never silently edits `settings.json`.
- **Ends with** — rules amended, mechanisms applied or proposed, memory entries added or updated, anything deleted as stale, or `No learnings captured.`
- **Unattended?** — No. It lists at most 5 to 8 candidates and waits for the user to reply with numbers or `none` before writing anything.

## context-gardening

- **Invoke** — `/gaffer:context-gardening`. No arguments; run quarterly, after a large architectural shift, or when `CLAUDE.md` feels stale.
- **Needs** — `ls` and `grep` to verify references, `git log --oneline -50` for pattern drift, `git diff --stat` after edits.
- **Reads** — no conventions table. `CLAUDE.md`, every file it imports with `@` or links by relative path within the repository, and every file under `.claude/memory/` including `MEMORY.md`. URLs and files outside the repository are skipped.
- **Changes or posts** — only approved candidates: edits to the target file with the drafted replacement; a new reference file under `docs/` with a one-line link left in place for a promotion; deletion of a memory file together with its `MEMORY.md` pointer.
- **Ends with** — the files changed and the candidates applied against skipped, or `No gardening applied.`
- **Unattended?** — No. It is advisory: it lists up to about 15 candidates and writes nothing before the user replies with numbers, `all` or `none`.

## The diagnose skill

- **Invoke** — `/gaffer:diagnose`, or model-invoked when the user says "diagnose this", "debug this", reports a bug or describes a performance regression. It is a skill, not a command, so it has no argument form.
- **Needs** — a fast, deterministic, agent-runnable pass/fail signal for the bug, which Phase 1 builds before anything else and refuses to proceed without. The last-resort human-in-the-loop form refers to `scripts/hitl-loop.template.sh`.
- **Reads** — `CONVENTIONS.md` → *Diagnose*, the plugin default then the repository's section, and any document it links; then the project's own navigation (`CLAUDE.md`, README, top-level docs).
- **Changes or posts** — a feedback loop (a failing test, script or harness); tagged instrumentation (`[DEBUG-<id>]`) that must all be removed before done; a regression test written before the fix where a correct seam exists, with the absence of a seam recorded as a finding where none does; the fix; throwaway prototypes deleted or moved to a marked debug location; the confirmed hypothesis stated in the commit or PR message.
- **Ends with** — the Phase 6 checklist: original repro no longer reproduces, regression test passes or its missing seam is documented, instrumentation removed, prototypes gone, the correct hypothesis recorded, and a post-mortem on what would have prevented the bug.
- **Unattended?** — Mostly. It shows its 3 to 5 ranked hypotheses to the user before testing them but does not block on a reply, proceeding with its own ranking when the user is away. It stops and asks when it genuinely cannot build a loop, listing what it tried and what it needs: an environment, a captured artefact, or permission to add temporary production instrumentation.

## The no-chmod hook

- **Invoke** — not invoked by name. `hooks/hooks.json` registers `bash "${CLAUDE_PLUGIN_ROOT}/hooks/no-chmod.sh"` as a `PreToolUse` hook on every Bash call, with no `if` clause: the script's own segment scan filters. `no-chmod.sh --check '<command>'` classifies one command string for CI or manual use, exiting 1 with the refusal when it would be blocked and 0 otherwise.
- **Needs** — `bash` and `awk`. It needs no executable bit. It fails open with an announcement on stderr when a tool is missing or the hook input is unparseable; the one path that fails closed is a refusal already decided that cannot be written out.
- **Reads** — the hook JSON on stdin, from which it takes the command. It reads no conventions file.
- **Changes or posts** — emits a `deny` decision for a command segment headed by `chmod` that would set the executable bit (`chmod +x`, `chmod u=rx`, `chmod 755` and friends), with a message naming `bash script.sh` as the alternative and `git add --chmod=+x <path>` for recording the bit on a committed file. Forms that cannot set the bit (`chmod 644`, `chmod -x`, `chmod u+w`) and undecidable modes (`--reference=`, a `g+u` copy form) pass through to the repository's own `Bash(chmod:*)` ask rule. A `chmod` reached through `find -exec`, `xargs` or `bash -c` is not seen; these limits are pinned as allow-cases in `hooks/no-chmod.tests.sh`, which is the specification.
- **Ends with** — exit 0 with no objection, or the deny decision carrying the refusal text. `GAFFER_ALLOW_CHMOD=1` makes hook mode a no-op, announced on stderr; `--check` ignores it.
- **Unattended?** — This is its purpose: in a repository that keeps `Bash(chmod:*)` on `permissions.ask`, `chmod +x` stalls an interactive run until a human answers and is silently denied in a headless one, so the hook redirects the call instead of letting the run stall or degrade. A plugin cannot set permission rules, so the ask rule stays the repository's to keep as the fail-open backstop ([`../README.md`](../README.md), *What a repository needs*).
